# Prevent rapid Send from stopping a new Run

**Status:** ready-for-agent

## Agent Brief

**Category:** bug
**Summary:** Prevent a rapid second Send interaction from activating the Stop control rendered in the same location.

**Current behavior:**
When Send starts a Run, the Composer immediately replaces Send with Stop at the same pointer target. A double-click or two rapid clicks can therefore send once and stop the newly created Run a few milliseconds later.

**Desired behavior:**
A pointer sequence that submits a message must not also stop the Run it created. Stop should become available after a short, bounded activation guard, while remaining responsive to a deliberate later interaction.

**Key interfaces:**

- The Composer's transition from sendable to running state must distinguish the submission interaction from a later Stop command.
- `stop(threadId)` must not be invoked by a rapid follow-up click during the activation guard.
- Keyboard submission and intentional Stop behavior must remain unchanged outside the guard.

**Acceptance criteria:**

- [ ] Double-clicking Send dispatches exactly one Run and does not call Stop for that Run.
- [ ] Two rapid clicks on the Send/Stop location do not cancel the newly started Run.
- [ ] Stop becomes enabled after a bounded delay of no more than 500 ms.
- [ ] Clicking Stop after the guard cancels the active Run normally.
- [ ] A renderer regression test covers the public Send-to-Stop interaction.

**Out of scope:**

- Moving or redesigning the Send and Stop controls.
- Changing Runtime cancellation semantics after Stop is accepted.
