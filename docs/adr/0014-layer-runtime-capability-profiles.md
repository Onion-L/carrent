# Layer runtime capability profiles for skill discovery

Skill discovery has three distinct owners: Kimi's provider-owned `Skill` tool (Kimi discovers and reads project/user skills itself), the Carrent Bridge (other runtimes, external MCP clients, and the compatibility fallback), and the ACP host `fs`/`terminal` surface (services Carrent offers the provider, not extra permissions granted to it). After ACP `initialize`, Carrent classifies the runtime into a Runtime Capability Profile (`src/shared/runtimeCapabilities.ts`) from `agentInfo`; only Kimi versions confirmed by the archived probe (`scripts/verification/skill-visibility-probe.ts`) count as provider-native, and everything else keeps the conservative profile.

Bridge attachment is a pure, testable policy (`electron/chat/bridgePolicy.ts`) evaluated before `session/new` and `session/resume`, which always receive the same MCP server list. Provider-native Kimi runs omit the Bridge; the Bridge is the compatibility fallback, kept for runtimes and Kimi versions that are not provider-native. The `CARRENT_OMIT_PROVIDER_NATIVE_BRIDGE` grey-release flag that staged this flip has been removed, and the policy no longer special-cases runs with attachments or Local Path Context — those grants live on the ACP fs surface, not on the Bridge. The Run Interaction Server (`carrent_session`) is independent of this policy, and the Local MCP Server switch still governs the Bridge.

## Consequences

Provider-native Kimi skill discovery and reads run entirely on the provider side: the provider's own `Skill` tool plus the standing read-only grant for skill catalog roots on the ACP `fs/read_text_file` surface (ADR 0004), which is what keeps user-scope skill content readable without the Bridge. Bridge audit entries record `allow`, `deny`, or `error` outcomes (with an error code and, when available, the runtime id) for requests the Bridge actually handled; they never contain tokens or skill bodies. Provider-owned Kimi skill reads remain outside that audit surface, so product copy must say "Bridge reads are audited", never "all skill reads are audited".

The default was flipped from `attach` to `omit` for provider-native runs after rerunning the archived probe against Kimi 0.38.0 (2026-08-26): all 16 scenarios met their baselines, confirming provider-owned discovery for `.agents/skills` roots in project and user scope, including depth limits, name conflicts, and symlinked skill directories. The same matrix confirms provider-owned discovery does not cover `.codex/skills` roots, so provider-native Kimi versions will not surface `.codex/skills` skills while running Bridge-less; that gap is accepted, and any newly released, not-yet-probed Kimi version automatically falls back to `attach` until it is added to `KIMI_PROVIDER_NATIVE_SKILL_VERSIONS`.
