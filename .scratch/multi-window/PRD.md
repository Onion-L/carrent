# Multi-Window Support

Category: enhancement
Status: done

## Request

Allow Carrent users to open and use multiple application windows.

## Established

- Carrent currently creates one Main Window and focuses it for repeated launches.
- The existing Workspace/Project/Thread IA PRD deliberately excludes multiple Main Windows and cross-window state coordination.
- No existing multi-window implementation or matching `.out-of-scope/` record was found.
- This request reopens the earlier single-window product decision.
- Carrent Windows are peers. Every window provides complete navigation for Workspace, Project, Thread, and Settings views; there is no privileged Main Window or restricted auxiliary window.
- The same Thread may be open in multiple Carrent Windows.
- Messages, Run state, Agent Activity, Approval Requests, user questions, and other Thread state are shared. An action or update in one window appears in every window showing that Thread.
- An existing Thread has one shared Thread Composer State. Text, attachments, Runtime, model, and run mode changes in one window appear in every window showing the Thread.
- Any window showing a Thread may send, stop its Run, answer an Approval Request, or answer a user question. The application serializes these commands so the first valid state transition takes effect and duplicate or stale commands do not execute again.
- Workspace, Project, Thread, message, Thread Draft, Thread Composer State, Run, and Settings data are shared and synchronized across all windows.
- Each window independently owns its route, selection, browsing history, and presentation state.
- A Workspace-Project Association still has at most one Thread Draft. Its edits and promotion to a Thread appear in every window.
- The Thread context menu provides `Open in new window`. It creates a peer Carrent Window whose initial route is the selected Thread.
- Multi-window support adds no global keyboard shortcut, File menu command, or permanent title-bar button for creating an empty window.
- Repeated ordinary application launch focuses the most recently active existing window without creating a window or changing any route.
- A valid Thread deep link focuses the most recently active window already showing that Thread. If none shows it, the deep link navigates the most recently active window. A deep link never creates a window.
- Closing one of several windows destroys only that window. It does not quit Carrent or stop a Run, and the remaining windows continue presenting shared state. The closed window's route, history, and presentation state are discarded.
- On macOS, closing the final window leaves Carrent and its Runs active. Dock activation or repeated launch creates one window using normal recent-position recovery. On Windows and Linux, closing the final window requests application Quit.
- Explicit Quit on every platform ends Carrent. If Runs are live, Carrent uses the existing confirmation flow and cancels them only after confirmation.
- A normal application restart restores every window that was still open at Quit, including its route, bounds, and maximized state. It does not restore browsing history or transient pane state. Invalid routes use the established nearest-valid-parent fallback.
- A window explicitly closed before Quit is not restored.
- A Project owns one shared set of Terminal Tabs across every window. Output, active Tab, and process state are synchronized, and any window may send input or create and close Tabs.
- Closing a Carrent Window does not terminate a Terminal Tab. Existing Terminal Tab, Project removal, and application Quit rules remain authoritative.
- The Main Process owns authoritative shared application state and serializes commands from every window. Each command is validated against the latest state; the first valid transition is applied and broadcast, while stale or duplicate commands are rejected and their caller receives the latest state.
- Renderers do not persist competing full snapshots. An older window state can never overwrite newer data or recreate an object that another window removed.
- A shared PTY uses the dimensions of the Carrent Window whose terminal viewport currently has focus. Moving terminal focus to another window transfers resize authority; when no terminal viewport is focused, the PTY retains its last dimensions. Unfocused windows continue receiving output but cannot resize the PTY.
- A new window opens on the source window's display, inherits its normal bounds, and is cascaded approximately 24 pixels down and right while remaining inside the display work area. A maximized source does not cause the new window to start maximized.
- Carrent imposes no product-level window count limit. If Electron cannot create a requested window, the source window shows a non-blocking error and all existing windows remain unchanged.

## Agent Brief

**Category:** enhancement
**Summary:** Support multiple peer Carrent Windows backed by authoritative shared application, Run, and Terminal state.

**Current behavior:**
Carrent creates one Main Window. Repeated launch and deep links focus or navigate that window, application state is maintained as Renderer-owned snapshots, Run events target that Renderer, and Terminal Tabs are associated with its Renderer owner.

**Desired behavior:**
Carrent remains a single application instance but may own multiple peer Carrent Windows. Each window has complete navigation and independent route/history/presentation state. Workspace, Project, Thread, Composer, Run, Settings, and Terminal data are application-owned and synchronized across every window. The Main Process serializes mutations against authoritative state and broadcasts accepted changes so stale Renderers cannot lose or recreate data.

**Key interfaces:**

- Carrent Window lifecycle: track all windows, their activation order, routes, bounds, maximized state, Renderer readiness, and close state without a privileged Main Window.
- Window bridge: open the selected Thread in a new window, receive targeted navigation, report current route and geometry, and surface window-creation failure.
- Shared state protocol: expose revisioned application state plus command submission and change subscriptions; reject stale or invalid transitions without accepting competing full-snapshot writes.
- Run coordination: keep one application-level Run state per Thread, broadcast events to all windows, and make send, Stop, Approval Request, and user-question transitions idempotent.
- Terminal Session Manager: keep Terminal Tabs Project-owned, broadcast their state and output to every interested window, and transfer PTY resize authority with terminal focus.
- Window session persistence: save only windows open at application Quit and restore their route, bounds, and maximized state without restoring browser history, transient pane state, PTYs, or terminal output.

**Out of scope:**

- Multiple Carrent application instances or cross-process state coordination.
- Main/auxiliary window roles, separate Settings windows, or restricted secondary windows.
- Per-window copies of Threads, Composer State, Runs, Settings, or Terminal Tabs.
- Restoring browsing history, transient pane state, PTYs, terminal output, or terminal panel visibility after application restart.
- Cross-machine synchronization, collaborative multi-user editing, or remote windows.
