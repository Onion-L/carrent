# Deduplicate the stop-guard expiry scheduling in the Composer

**Status:** ready-for-agent

## Agent Brief

**Category:** enhancement
**Summary:** Unify the two copies of the stop-guard expiry logic introduced for issue 01, and store the guard's per-Thread state in one record instead of two parallel maps.

**Current behavior:**
The 500 ms Send-to-Stop activation guard (issue 01) schedules its expiry cleanup in two places: once when the guard begins, and once in an effect that re-arms cleanup. Both copies run the same shape of logic — a timer that, on expiry, checks whether the guard record for the Thread still matches the scheduled token and deletes it if so. The guard's per-Thread state is also split across two module-level maps keyed by the same Thread id, so the two must be kept manually in sync.

Any future change to the guard (duration, cleanup condition, token semantics) must be made in both places; missing one produces a subtle desync bug.

**Desired behavior:**
One shared expiry scheduler serves both call sites, and the per-Thread guard state lives in a single record (e.g. one map from Thread id to a guard entry holding both the expiry token and its cleanup handle). Behavior is unchanged: the guard still activates for a bounded delay of no more than 500 ms, and Stop still works normally after the guard.

**Key interfaces:**

- The Composer's stop-guard state — consolidate from two Thread-keyed maps into one Thread-keyed record.
- The guard expiry scheduling — a single internal helper both the guard-begin path and the re-arm effect call.
- `stop(threadId)` semantics — untouched.

**Acceptance criteria:**

- [ ] The expiry-check-and-delete shape exists exactly once in the codebase.
- [ ] Guard state for a Thread is held in one record; there is no second parallel map to keep in sync.
- [ ] The existing regression tests for issue 01 (rapid Send clicks, 500 ms bound, post-guard Stop) pass unmodified.
- [ ] No behavior change: guard duration and Stop responsiveness are identical to before.

**Out of scope:**

- Changing the 500 ms guard duration or the Send/Stop control layout.
- Any other Composer cleanup or refactoring beyond the stop-guard state and its expiry scheduling.
