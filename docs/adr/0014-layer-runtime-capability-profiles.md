# Layer runtime capability profiles for skill discovery

Skill discovery has three distinct owners: Kimi's provider-owned `Skill` tool (Kimi discovers and reads project/user skills itself), the Carrent Bridge (other runtimes, external MCP clients, and the compatibility fallback), and the ACP host `fs`/`terminal` surface (services Carrent offers the provider, not extra permissions granted to it). After ACP `initialize`, Carrent classifies the runtime into a Runtime Capability Profile (`src/shared/runtimeCapabilities.ts`) from `agentInfo`; only Kimi versions confirmed by the archived probe (`scripts/verification/skill-visibility-probe.ts`) count as provider-native, and everything else keeps the conservative profile.

Bridge attachment is a pure, testable policy (`electron/chat/bridgePolicy.ts`) evaluated before `session/new` and `session/resume`, which always receive the same MCP server list. The default stays `attach`; omitting the Bridge for provider-native Kimi runs is gated behind the `CARRENT_OMIT_PROVIDER_NATIVE_BRIDGE=1` grey-release flag and never applies to runs with attachments or Local Path Context. The Run Interaction Server (`carrent_session`) is independent of this policy, and the Local MCP Server switch still governs the Bridge.

## Consequences

Bridge audit entries record `allow`, `deny`, or `error` outcomes (with an error code and, when available, the runtime id) for requests the Bridge actually handled; they never contain tokens or skill bodies. Provider-owned Kimi skill reads remain outside that audit surface, so product copy must say "Bridge reads are audited", never "all skill reads are audited". The 0.38.0 probe matrix confirmed provider-owned discovery for `.agents/skills` roots but not for `.codex/skills` roots, and a deeper scan than the Skill Catalog, so the default stays `attach`; it may only flip to `omit` once the full matrix passes for the supported Kimi versions, and older or unprobeable versions always fall back to `attach`.
